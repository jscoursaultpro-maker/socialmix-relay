## 12. Restitution AfterGlow

### Côté serveur — débloqué

`/api/host/parties/by-user` (`server.js` L4032) filtre **sur les champs stockés** avant de les recalculer :
```js
{ $match: { participantCount: { $gte: 3 }, trackCount: { $gte: 20 } } }
```
FTMP63 porte aujourd'hui `trackCount: 98` et `participantCount: 4` : **la soirée passe le filtre.**
Avant la restauration des compteurs, `trackCount` valait 0 → la soirée était exclue du
rafraîchissement, quel que soit son contenu réel.

`/api/host/parties/:code/details` (L4079-4130) résout les titres via `$ifNull: ['$_track.title', '$title']` : **ce chemin n'a jamais produit de « Unknown Track »** — la correction qui visait ce symptôme ne portait pas sur le bon appelant.

### Côté iOS — non corrigé

Deux lignes expliquent le « 0 titres » persistant sur l'écran AfterGlow :
- `PartyStore.swift` L22 — `var trackCount: Int { tracks.count }` : le compteur affiché vient du **cache local**, jamais du serveur.
- `PartyStore.swift` L752 — `localParties.append(stubWithCounts)` : `refreshPartiesFromServer` **n'ajoute que les soirées nouvelles** et ne met jamais à jour une entrée déjà en cache.

Conséquence : même avec un serveur désormais juste, l'entrée FTMP63 déjà présente dans le cache conservera `0 titres` jusqu'à ce qu'elle soit remplacée. **Le correctif serveur ne suffit pas, un correctif iOS est nécessaire.**

## 🚨 Anomalies détectées

### [P0] 97/97 écritures d'historique rejetées — enum `provider` divergent
**Fait.** `success: 0, failed: 97, skipped: 0`. `Party.streamingProvider` accepte `appleMusic`,
`apple`, `youtube` ; `HostPlaybackHistory.provider` ne les connaissait pas. Échec silencieux car
`party.hphCounters` n'était pas initialisé → `TypeError` dans une IIFE asynchrone non capturée.

**Élargissement (doctrine 3.9).** 1 929 documents manquants sur **194 soirées**. Le correctif
antérieur `55e2f73` ne mappait que `appleMusic` : les 7 soirées en `youtube` restaient à zéro.

**Reproductibilité.** 100 % — toute soirée dont le provider n'était pas dans l'enum.

**État : CORRIGÉ.** `lib/providers.js` (source unique des enums) + hook `pre('validate')` de
normalisation + `lib/recordPlayback.js` partagé par `host:trackUpdate` **et**
`host:liveTrackDetected` (ce dernier n'écrivait aucun HPH). 1 929 documents restaurés,
12 049 → 13 978. Écriture temps réel vérifiée sur JAN9JQ le 03/10.

### F. Note méthodologique sur une erreur de ce rapport, corrigée

Au premier passage, j'avais attribué le dépassement de la limite de tri de 32 Mo au poids des
photos en base64 dans les documents `Party`. **C'est faux et je le retire :** le document `Party`
le plus lourd de la base pèse **0,76 Mo**, et FTMP63 **0,23 Mo**. La cause réelle est le tri sur un
champ non indexé. La même erreur sous-jacente, côté production, est celle de
`computeUserStats` — ce qui en fait un défaut de requête, pas un problème de volumétrie.
